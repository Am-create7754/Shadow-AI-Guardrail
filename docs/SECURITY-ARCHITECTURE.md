# Security architecture: defence in depth against Shadow AI

"Shadow AI" is employees sending company data to AI services the organisation
does not control. No single control can stop it: a gateway only sees traffic
sent to it, and a browser extension only sees browsers it is installed in. This
project therefore uses **four layers**, each covering gaps of the others, and
states what remains.

```
             ┌─────────────────────────── 1. Network ───────────────────────────┐
             │  DNS filter / web proxy / firewall: AI sites and provider APIs    │
             │  blocked for every device, except via the gateway                 │
             │   ┌──────────────── 2. Managed browser ─────────────────┐         │
  employee ──┼──►│ force-installed extension checks prompts + uploads  │──► AI site (covered list)
             │   │ uncovered AI sites blocked, no Incognito / Guest    │         │
             │   └─────────────────────────────────────────────────────┘         │
             │   ┌──────────────── 3. Gateway (sanctioned path) ───────┐         │
  apps, IDE, ┼──►│ inspect → redact / approve / block → provider       │──► provider API
  dashboard  │   │ output inspection, leak-safe streaming              │  (only the gateway
             │   └─────────────────────────────────────────────────────┘    may reach it)
             └───────────────────────────────────────────────────────────────────┘
                 4. Evidence: HMAC-chained audit log, signed checkpoints, dashboard
```

## 1. Network layer - the only control independent of the device's software

Generated by `deploy/chrome-policy/New-GuardrailPolicy.ps1` into
`ai-blocklist.txt` from `deploy/ai-domains.json`.

| Rule | Where | Purpose |
|---|---|---|
| Block uncovered AI sites (`block_in_browser`) for all clients | DNS filter (e.g. Pi-hole, Windows DNS policies, a secure web gateway) or proxy ACL | Catches other browsers, unmanaged apps, personal browser profiles |
| Allow covered AI sites (`covered_by_extension`) only from managed devices; block for everything else | Proxy with device identity / NAC, or separate network segments | A covered site is only safe where the extension is enforced |
| Allow provider APIs (`provider_apis_gateway_only`) **only from the gateway host** | Egress firewall / proxy | Applications and scripts cannot call AI APIs directly with personal keys; the gateway is the only route |
| Inspect or block TLS to unknown AI endpoints | Secure web gateway categories ("Generative AI") | Covers services not on the list |

Example egress rule (any firewall): *allow `gateway-host` → `api.openai.com:443`,
`generativelanguage.googleapis.com:443`; deny all other hosts → those
destinations*. Example Squid ACL:

```
acl ai_api dstdomain api.openai.com api.anthropic.com generativelanguage.googleapis.com
acl gateway src 10.0.5.10/32
http_access allow gateway ai_api
http_access deny ai_api
```

Limits: DNS filtering is bypassed by DNS-over-HTTPS unless DoH is blocked or
managed (Chrome policy `DnsOverHttpsMode`); domain lists age; devices off the
company network (VPN split tunnelling, home Wi-Fi) need an always-on VPN or a
cloud secure web gateway agent.

## 2. Managed browser layer

`extension/` + `deploy/chrome-policy/`. Force-installed and pinned by policy,
it checks prompts and file uploads on ChatGPT, Claude, Gemini and Copilot before
the site receives them; uncovered AI sites, Incognito and Guest mode are blocked.
See `extension/README.md` for the trust model (API key only in the service
worker, real-user-only checks, fail closed).

## 3. Gateway layer - the sanctioned path

`backend/`. The approved way to use AI: the dashboard playground, the
OpenAI-compatible API for applications and IDE plugins. Inspection before
forwarding, typed placeholders, approval workflow with separation of duties,
output inspection, leak-safe streaming. Making this path convenient reduces
the incentive to use unsanctioned tools.

## 4. Evidence layer

HMAC-SHA256 chained audit events, Ed25519 checkpoints and an external anchor;
the dashboard shows decisions, detected entity types and checks per AI site
(metadata only, never prompt text). A chain is tamper-*evident*, not
tamper-proof: see `docs/AUDIT.md`.

## Threat model (summary)

| Threat | Actor | Layer(s) that stop it | Residual risk |
|---|---|---|---|
| Developer pastes a credential into ChatGPT by accident | Careless employee | 2 (prompt check), 4 (record) | Unrecognised editor markup after a site redesign; secret formats the detectors miss (`docs/EVALUATION.md`) |
| Uploads a `.env` / source file to an AI site | Careless employee | 2 (upload check) | Contents of PDF/Office/images are not inspected - blocked by default instead |
| Uses an AI site not on the list | Employee | 2 (URLBlocklist), 1 (DNS/proxy) | New services until the list is updated; generic "AI" proxy categories help |
| Switches the extension off, uses Incognito | Employee | 2 (force-install, Incognito off) | Unmanaged browser - needs 1 and application control |
| Uses another browser or a personal device | Determined employee | 1 (network), application control (AppLocker / Intune) | Personal devices on mobile data are outside any company control: policy and training |
| Script calls an AI API with a personal key | Developer | 1 (egress only from gateway) | Exfiltration via general-purpose channels (e-mail, file sharing) is out of scope |
| Hostile or compromised AI site page | External | 1, 3 (send sensitive work through the gateway) | The page sees keystrokes before any check; the extension does not defend against the site itself |
| Page script abuses the extension as an oracle | External | 2 (only real user input starts a check) | A 1-second window after real input for form submissions |
| Secret leaks in a model answer | Model / provider | 3 (output inspection, stream guard) | Values only later recognisable as secrets in a stream; code checks are pattern-based |
| Audit log tampering | Insider with DB access | 4 (HMAC chain, signed checkpoints, external anchor) | Holder of both keys and all anchors can rewrite history; export checkpoints off-host |
| Gateway compromise | Attacker | Hardening (`docs/DEPLOYMENT.md`), least privilege, separate keys | A compromised gateway sees all prompts sent through it |

A full STRIDE analysis is part of the Phase 8 academic deliverables.

## What this project does not claim

It does not stop a determined insider with a personal device, does not inspect
the contents of binary documents, and does not replace data-loss-prevention,
endpoint management or staff training. It makes accidental leaks through the
common paths unlikely, makes deliberate ones harder, and leaves evidence.
