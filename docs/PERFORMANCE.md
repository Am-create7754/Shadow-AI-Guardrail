## Reading the numbers

* The audit log is the deliberate bottleneck: every decision is committed (HMAC
  chain, `BEGIN IMMEDIATE`) before anything is forwarded, so writes are
  serialised. That is the fail-closed design, not an accident.
* Scaling: more Uvicorn workers help detection (CPU-bound) but not audit writes
  on SQLite; PostgreSQL (row lock on the chain head) is the path for higher
  write rates (implemented, not load-tested here).
* With a real provider, model latency (hundreds of ms to seconds) dominates;
  the gateway adds the inspection and audit time measured above.

## Variance

Numbers on this laptop vary by up to ~2-3x between runs (OneDrive sync, antivirus
scanning, power management - visible even in the CPU-only engine benchmark,
which ranged from 0.5 to 1.2 MB/s). The run before this one, with the same code,
measured 134 req/s and p99 274 ms for short inspections. Treat the table as an
order of magnitude on a busy developer laptop, not a benchmark.

## Defects found by load testing (fixed)

| Finding | Cause | Fix | Effect |
|---|---|---|---|
| p99 latency of 2.5-6.5 s with p50 of 50-200 ms | Every API-key request wrote `last_used_at`, competing with audit writes for SQLite's single write lock; SQLite's busy handler retries with growing sleeps | `last_used_at` written at most once per minute per key (best effort, `IMMEDIATE` transaction) | p99 0.3-0.85 s, throughput 2-3x (same machine, consecutive runs) |
| ~1 in 300-1,500 requests answered `503 audit_unavailable` | The audit log's own secret scan treated ~1 in 10,000 random request ids (`uuid4().hex`) as card numbers (a Luhn-valid digit run) and refused the event - fail closed, so the request failed | Generated 32-hex identifiers are not scanned as content; card numbers anywhere else still are | 0 errors in 2,500 requests; `test_generated_ids_that_look_like_card_numbers_are_accepted` (fails on the old code) |
| Audit failures left no trace in the server log | `_audit_or_fail` refused without logging | Logged by exception type and request id (never data) | Made the second finding diagnosable |

Also added: **group commit** for audit appends - concurrent requests' events are
committed in one transaction (each request still waits for its own record to be
durable before anything is forwarded), and in-process writers queue instead of
contending for the database lock. Tests: `tests/test_audit_group_commit.py`
(batching, a failed batch fails every caller, cancelling the committing caller
does not fail the others).
